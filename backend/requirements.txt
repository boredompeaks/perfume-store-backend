# Pointer file. The pinned dependency set lives in requirements.lock, which is
# generated from requirements.in by the pinned pip-tools:
#
#     pip-compile --generate-hashes --no-emit-index-url --no-emit-trusted-host \
#         --output-file=requirements.lock requirements.in
#
# (Same command as the one in requirements.in; the lock's own generated header
# prints an extra `--no-index` from pip-compile's internal invocation, which
# this command does not pass.)
#
# Install with either name - this pointer and the lock resolve to the identical
# set, which is the point of keeping the pointer: `pip install -r
# requirements.txt` (the documented developer command in backend/README.md) and
# `pip install -r requirements.lock` (what CI runs) cannot disagree.
#
# Both this file and requirements.lock must be present in any directory that
# installs from this pointer: pip resolves the `-r` include RELATIVE TO THIS
# FILE, so a build context that copies only requirements.txt gets an error
# rather than a partial install. That is why backend/Dockerfile copies both.
#
# Why a lock at all: transitive dependencies were resolved at install time, so
# a commit that changed no Python could pull a different version of a library
# and turn a green suite red. Every direct pin here is still a decision recorded
# in requirements.in, next to the reason it was made.
-r requirements.lock
