# API contract — write endpoints (SPEC-9-08, [R-9.5])

Per-endpoint contract for the **write** endpoints (POST/PUT/PATCH/DELETE) this
API mounts, enumerated from the actual urlconfs (`config/urls.py` + the app
urlconfs both families mount) rather than from an earlier version of this list.
The columns mirror the §9.5 write-endpoint checklist (spec lines 3383–3403)
point for point:

> 1. Required permission. 2. Required request fields. 3. Validation
> constraints. 4. Expected state transition. 5. Transaction boundaries.
> 6. Idempotency requirements. 7. Audit-log behaviour. 8. Success response.
> 9. Possible errors. 10. Whether the operation triggers notifications or
> background jobs.

Read endpoints (GET) are outside the checklist's scope ("For every write
endpoint") and are listed nowhere here — the customer/admin order-detail and
list GETs shipped in SPEC-9-04/9-07 are therefore excluded, exactly as the
spec text prescribes. The Django admin site (`/admin/...`) is HTML chrome,
not part of this API contract: its change forms and its confirmation-gated
actions are not JSON endpoints. SPEC-E-02's refund-request approval/refusal
lives there and is recorded under [Out of scope, by decision](#out-of-scope-by-decision)
rather than as a table row.

**Versioned mirrors.** Every path below except the provider webhook is served
on two families from one urlconf object (no view duplication): the legacy
`/api/...` paths shown in the table, and the §9 family mounts under
`/api/v1/` — `/api/v1/account/...` (accounts),
`/api/v1/store/products|cart|orders|shipping/...` (store),
`/api/v1/admin/...` (admin orders seam). The webhook is the one exception: it
is called by the provider, so it is mounted only at
`/api/v1/webhooks/razorpay/` and has no legacy alias. One contract, two
mounts (one for the webhook); the mirror is noted once here rather than per
row.

Every JSON error response — row's "Possible errors" cells included — is the
uniform envelope `{"error", "code", "details"}` (SPEC-9-03; the one shape is
built in `common/errors.py`). Since ENVELOPE-WIRE it is the bytes on the wire,
not merely an in-process payload: the DRF exception handler (wired as
`REST_FRAMEWORK["EXCEPTION_HANDLER"]`) envelops every DRF exception before
rendering, and the error-envelope middleware rewrites the ad-hoc
`Response({"error": ...})` bodies that raise no exception — one shape, two
producers, and an already-enveloped body passes through untouched. `code` is
the status-family label (`validation_error`, `not_authenticated`,
`permission_denied`, `not_found`, `method_not_allowed`, `conflict`,
`throttled`; 5xx responses carry `server_error`). The provider webhook's
  refusal bodies are the one exception in kind: it is a server-to-server
  endpoint, but its `{"error": ...}` bodies go through the same middleware,
  so the envelope is uniform there too.

## Out of scope, by decision

- **Django admin HTML writes.** The `/admin/...` change forms, the saved-filter
  endpoints and the confirmation-gated actions are form POSTs that redirect
  back to a changelist; they write through the admin site, not this JSON API,
  so they get no row above.
- **SPEC-E-02 refund-request approve/reject.** These are two admin actions on
  `RefundRequestAdmin` (`approve_requests`, `reject_requests`), reached from
  the admin changelist, both gated by `refunds.create` and both requiring a
  confirmation note. Approval locks the order and then the pending request,
  derives the amount from the filed `items` (whole order = the remaining
  refundable balance; otherwise the frozen line subtotals) and hands it to the
  one refund writer with a deterministic `refund-request-<pk>` idempotency key,
  so a replay cannot pay twice; refusal only stamps
  `status`/`decided_by`/`decided_at`. Neither action moves money outside
  `orders.refunds.issue_refund`, and the admin `LogEntry` plus that writer's
  privileged-action record are the audit trail.
