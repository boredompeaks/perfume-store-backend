# API contract — write endpoints (SPEC-9-08, [R-9.5])

Per-endpoint contract for every **write** endpoint (POST/PUT/PATCH/DELETE) in the
current API, enumerated from the actual urlconfs (`config/urls.py` + the app
urlconfs both families mount). The columns mirror the §9.5 write-endpoint
checklist (spec lines 3383–3403) point for point:

> 1. Required permission. 2. Required request fields. 3. Validation
> constraints. 4. Expected state transition. 5. Transaction boundaries.
> 6. Idempotency requirements. 7. Audit-log behaviour. 8. Success response.
> 9. Possible errors. 10. Whether the operation triggers notifications or
> background jobs.

Read endpoints (GET) are outside the checklist's scope ("For every write
endpoint") and are listed nowhere here — the customer/admin order-detail and
list GETs shipped in SPEC-9-04/9-07 are therefore excluded, exactly as the
spec text prescribes. The Django admin site (`/admin/...`) is HTML chrome,
not part of this API contract.

**Versioned mirrors.** Every path below is served on two families from one
urlconf object (no view duplication): the legacy `/api/...` paths shown in
the table, and the §9 family mounts under `/api/v1/` —
`/api/v1/account/...` (accounts), `/api/v1/store/products|cart|orders/...`
(store), `/api/v1/admin/...` (admin orders seam). One contract, two mounts;
the mirror is noted once here rather than per row.

Every JSON error response — row's "Possible errors" cells included — is
wrapped in the uniform envelope `{"error", "code", "details"}` (SPEC-9-03
middleware; `code` is the status-family label, e.g. `validation_error`,
`permission_denied`, `not_found`, `conflict`, `throttled`).

| POST `/api/orders/checkout/` | `IsAuthenticated` (JWT) | `full_name`, `phone`, `address`, `city`, `state`, `pincode`; `coupon_code` optional (explicit payload wins over the persisted cart coupon); `Idempotency-Key` header optional | Session cart exists and is non-empty; every address field present; per-line stock advisory (authoritative re-check at verify); coupon rules re-run at checkout; key length ≤ 128 | `Order` created `pending` + frozen `OrderItem` snapshot rows (product_name/sku/variant_name/price/subtotal); cart emptied and coupon usage counted only at verify — not here | One `transaction.atomic()` block: user-row lock, cart-row lock, dedup probe on (user, key) inside the lock, order-number mint with IntegrityError retry (unique constraint as concurrency authority) | Keyed: every replay with the same key returns the ORIGINAL order (unique (user, key) constraint backstops the lock); keyless: SPEC-21-1 duplicate-pending guard windows the same user+cart resubmission | `ORDER_CREATED` AuditEvent | 201 order body (OrderSerializer) | 400 missing fields/empty cart/oversell advice/coupon invalid/key too long; 404 cartless | None (the confirmation email fires at payment verify) |

| POST `/api/orders/payment/` | `IsAuthenticated` | `order_id` | Order exists and is owned by the caller (uniform 404 — no existence leak); status must be `pending` | `razorpay_order_id` persisted once on the order (gateway intent) | Intent save + `PAYMENT_INITIATED` AuditEvent commit together; the reuse path writes nothing | Idempotent — repeat calls reuse the stored intent; no second gateway call, no second event | `PAYMENT_INITIATED` (first intent only) | 200 `{order_id, razorpay_order_id, amount (paise), amount_in_rupees, currency, key_id}` | 400 missing `order_id` / order not payable; 404 unknown/foreign order; 500 gateway failure (logged, re-raised) | Gateway call to Razorpay (external side effect); no emails/jobs |
| POST `/api/orders/payment/verify/` | `IsAuthenticated` | `order_id`, `razorpay_order_id`, `razorpay_payment_id`, `razorpay_signature` | HMAC signature verified against the gateway payload; order owned + `pending`; gateway order id matches; stock sufficiency re-checked under lock; coupon still redeemable | `pending` → `confirmed`; `paid_at` stamped once (or-guard, never mutated); stock decrements + `StockMovement(SALE)` ledger rows; coupon `used_count` + 1; cart lines removed | One `transaction.atomic()` block with `select_for_update()` on the order, the products (cart-insertion order) and the coupon — any failure rolls the whole verification back | Idempotent — a replay of an already-verified order is refused at the already-processed gate with `paid_at` identical; nothing re-executes | `payment.verified` + `order.paid` AuditEvents inside the block | 200 `{message, order_id, status, razorpay_payment_id}` | 400 missing fields/bad signature/already processed; 409 stock conflict or coupon invalidated since intent | `notifications.dispatch(ORDER_PAID)` → confirmation email inside the block (dispatch never raises; SMTP failure logged, payment stays confirmed) |
| POST `/api/admin/orders/<id>/fulfill/` | `orders.fulfill` role (support/admin) via `HasOrdersFulfill`; no throttle scope (staff-gated) | None (path id) | Order exists; `transition_allowed(current, next)` — the state machine is the single gate; fulfilment advances one legal step per call: pending→confirmed→shipped→delivered | Order status advanced one step along the fulfilment path | `transaction.atomic()` + `select_for_update()` on the order row — two concurrent fulfils cannot both pass the gate on a stale status | Not idempotent by design — each accepted call is one visible transition; a terminal state (or any revoked edge) is a 409, never a silent re-run | LogEntry CHANGE via `log_api_action` ("Fulfilled via API: status moved to …") | 200 `{message, order_id, status}` | 403; 404 unknown order; 409 illegal transition (machine's allowed set in `details`) | None |

## Provenance

- Generated 2026-09-20 (SPEC-9-08, docs-only). Source of truth: `config/urls.py`
  and the app urlconfs (`accounts/urls.py`, `products/urls.py`, `cart/urls.py`,
  `orders/urls.py`) plus the views they mount. When an endpoint changes, this
  row changes with it.
- Checklist text: spec lines 3383–3403 ("For every write endpoint, specify:
  …"), mirrored verbatim as the column set above.
- Throttle scopes are recorded inside the permission column (point 1) because
  the checklist's ten points have no separate throttle slot; scopes come from
  the views (`auth`, `recovery`, `cart`, `coupon`) and `THROTTLE_*_RATE`
  settings.
